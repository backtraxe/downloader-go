# Emoji 作者展示与可搜索标签设计

日期：2026-11-22

## 问题与目标

Telegram 不是可靠地把 `#😀` 当作可搜索话题标签。当前实现虽然保留了 emoji，
但失去了按作者查找的用途。目标是同时保留原始作者显示和稳定的文本搜索标签，
不依赖猜出的语义别名或运行时翻译。

## 已选方案

将“原文展示”与“搜索标签”分开，而不是扩大 hashtag 字符集或简单删除 emoji。

### 不含 emoji 的作者名

仍以 Unicode 字母、数字、下划线及组合字符生成普通标签，不额外展示作者原文，
保持现有 caption 简洁。此处的 emoji 以 Unicode symbol 类别判定。

### 含 emoji 的作者名（用户最终确定的规则）

仅把昵称中的 emoji 部分替换为 `emoji_<码点>`，普通文字仍按原规则形成标签。
码点使用 lowercase hex，连续组合表情的码点以 `_` 连接；emoji 部分结束后恢复
普通文字时插入 `_` 分隔，避免编码与后续字母连成不可区分的一段。

例如（用户明确指定的形式）：

```text
#小明emoji_1f600 #xiaohongshu
作者：小明😀
标题
```

纯 `😀` 为 `#emoji_1f600`，`👩‍💻` 为 `#emoji_1f469_200d_1f4bb`。
ZWJ、变体选择符和肤色修饰符也参与编码，普通文字不整体转为码点。
这种形式不采用自然语言别名，在本地规则内稳定。Telegram 客户端自身的索引行为
不在本程序控制内。

## 约束与非目标

- 不改变 caption 所在图片位置、媒体分组、目录布局或作者原始下载元数据。
- 文件夹仍保留原始 emoji，不改成码点文本。
- 不调用外部翻译服务，不把某个 emoji 猜测成“笑脸”等语义名称。
- 空作者和纯分隔符作者仍省略作者标签；不能被误认为 emoji 数字别名。
- 保持现有 `BuildCaption` 的总长度上限，截断时保证合法 UTF-8。
- 测试完全离线，覆盖普通作者、混合作者、纯 emoji 及组合 emoji。
- 同步更新此前“#emoji 可直接作为标签”的行为说明，不再暗示其可搜索。

## 验证

- `MakeTag` 仅把作者名中的 emoji 部分替换为小写码点标签，普通文字维持搜索标签规则。
- `BuildCaption` 对普通作者不增加原文行，对含 emoji 的作者精确保留原文。
- 作者目录继续通过现有 emoji 回归测试。
- 运行 `CGO_ENABLED=0 go test ./...`、`CGO_ENABLED=0 go vet ./...`、
  `git diff --check`。
